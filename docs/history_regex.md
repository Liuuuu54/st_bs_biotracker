# 历史消息正则处理

## 处理顺序

历史消息不会先合并再跑正则，而是：

1. 逐楼层读取原始消息正文。
2. 当前楼层按正则列表从上到下执行。
3. 处理后的楼层进入下一楼。
4. 所有楼层处理完成后，才由 Tracker 合并/消费。
5. 原始宿主聊天对象不会被修改。

## 规则

每条规则都有：

- **提取**：从当前文本中抽取匹配结果。
- **排除**：从当前文本中删除匹配结果。
- **启用/禁用**：禁用规则不会执行。
- **顺序**：上下移动决定执行顺序。

正则输入支持：

```text
/<content>(.*?)<\/content>/gs
```

也支持不写 `/.../flags`：

```text
<content>(.*?)<\/content>
```

flags 按 JavaScript `RegExp` 规则处理，`g` 是否存在保持原样：没有 `g` 时只处理第一个匹配，有 `g` 时处理全部匹配。

### 提取规则的捕获组

如果提取正则存在捕获组，会取**第一个有定义的捕获组**。例如：

```text
/<content>(.*?)<\/content>/gs
```

会得到 `<content>` 与 `</content>` 之间的内容，而不是整个标签。

没有捕获组时，提取完整匹配。

## 预览

设置页的「预览当前楼层提取结果」：

- 默认预览送入分析的最近 `contextSize` 楼。
- 可以填写 1-based 的开始/结束楼层。
- 只显示处理后的结果，不显示原始文本。
- 没有规则时，结果与原始楼层正文一致。
- 预览不会修改原始聊天。

## 注意

提取规则本身是流水线操作。例如：

```text
规则1：提取 <A>...</A>
规则2：排除 debug
规则3：提取 [B]...</B>
```

规则 2 只能看到规则 1 输出的文本；规则 3 只能看到规则 2 输出的文本。这是为了保证规则排序具有明确且可复现的意义。
