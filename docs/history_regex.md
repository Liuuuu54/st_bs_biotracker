# 历史消息正则处理

## 处理顺序

历史消息不会先合并再跑正则，而是：

1. 逐楼层读取原始消息正文。
2. 当前楼层按正则列表从上到下执行.
3. 处理后的楼层进入下一楼。
4. 所有楼层处理完成后，才由 Tracker 合并/消费。
5. 原始宿主聊天对象不会被修改。

## 规则

每条规则都有：

- **提取**：从当前文本中抽取匹配匹配结果并替换当前消息文本。
- **排除**：从当前文本中删除匹配到的内容（相当于用空字符串替换匹配项）。
- **启用/禁用**：禁用的规则不会在流水线中执行，方便临时停用而不需要删除。
- **顺序**：可通过“↑ / ↓”按钮上下移动规则，从而改变在流水线中的执行顺序。

正则输入支持以下两种格式：

1. 带斜杠和修饰符（flags）的正则表达式字面量：
   ```text
   /<content>(.*?)<\/content>/gs
   ```
2. 不带斜杠的纯正则表达式：
   ```text
   <content>(.*?)<\/content>
   ```

修饰符（flags）会按照 JavaScript 的 `RegExp` 规范执行：
- 如果没有 `g` (global) 修饰符，则只替换或提取第一个匹配项。
- 如果存在 `g` 修饰符，则替换或提取所有的匹配项。

### 提取规则的捕获组处理

对于**提取（extract）**类型的规则：
- 如果正则表达式中**包含捕获组**（如括号 `(...)`），提取逻辑会取**第一个有定义的捕获组**。例如匹配 `/<content>(.*?)<\/content>/gs`，将只保留捕获组中的内容，而自动剥离外层的 `<content>` 和 `</content>` 标记。
- 如果正则表达式中**没有捕获组**，则提取完整匹配的文本（即整个匹配字符串）。

## 注意

历史消息正则处理是基于**流水线（Pipeline）**模型的独立过滤机制。这意味着前一个规则的输出文本，会作为后一个规则的输入文本继续被处理：

```text
原始消息文本 ──> [规则 1 (例如: 提取 <A>...</A>)] ──> 处理后文本A 
              ──> [规则 2 (例如: 排除 debug)] ──> 处理后文本B 
              ──> [规则 3 (例如: 提取 [B]...</B>)] ──> 最终输入给 Tracker 的文本
```

该模型确保了正则处理的顺序具有明确且可复现的意义，且完全在内存中执行，不会污染、改写或损坏宿主（SillyTavern）保存在本地的原始聊天记录。
